Verdict. The codebase is small (38 classes, no custom auto-configuration, no XML) and the migration is mechanical for ~80% of it (javax → jakarta imports, JUnit 4 → 5, one removed dialect property). 03Migration path: stepping stones, not a leap

Spring's own guidance is to upgrade one major at a time so each release's deprecation warnings point at the next break. Because 1.5 → 4.1 crosses four majors, we stop at 2.7 and 3.5 (both the last minors of their line) and verify the app at each.

Figure 3 — Three verified stops. Each stop must pass mvn verify and the manual smoke script (signup → login → deposit → transfer → appointment → admin API) before moving on.

Why not go straight to 4.1? You can, and for a 38-class app it is tempting. The intermediate stops exist for one reason: Step 1 surfaces the ID-generator and JSON-date behaviour changes with the codebase otherwise unchanged, so any regression is unambiguously attributable. Once those two are settled, Steps 2 and 3 are purely compile-driven and can be done in a single branch.

config/SecurityConfig.java compile security semantics

This is the largest rewrite. Five distinct removals hit this one file: WebSecurityConfigurerAdapter (gone in Security 6), antMatchers (gone in 6), @EnableGlobalMethodSecurity (gone in 7), the non-lambda .and() DSL (gone in 7), and AntPathRequestMatcher (gone in 7). Additionally, the public matcher "/error/**/*" on line 46 is not a valid PathPattern — ** is only permitted as the final segment — and Spring MVC 6+ uses PathPatternParser by default, so the pattern must become "/error/**". Finally, authorizeRequests() (FilterSecurityInterceptor) is replaced by authorizeHttpRequests() (AuthorizationFilter), which also authorises every dispatch type; the login/error forwards remain covered because /index and /error/** are public.

@EnableMethodSecurity            // prePostEnabled is the default

  public SecurityFilterChain filterChain(HttpSecurity http,
      AuthenticationProvider provider) throws Exception {
    http
      .authenticationProvider(provider)
      .authorizeHttpRequests(auth -> auth
        .requestMatchers(PUBLIC_MATCHERS).permitAll()
        .anyRequest().authenticated())
      .csrf(csrf -> csrf.csrfTokenRepository(
          CookieCsrfTokenRepository.withHttpOnlyFalse()))  // was .disable(); see note
      .cors(Customizer.withDefaults())   // was .disable(); see RequestFilter
      .formLogin(form -> form
        .loginPage("/index")
        .failureUrl("/index?error")
        .defaultSuccessUrl("/userFront")
        .permitAll())
      .logout(logout -> logout
        .logoutRequestMatcher(
          PathPatternRequestMatcher.withDefaults()
            .matcher("/logout"))   // GET logout kept; see note
        .logoutSuccessUrl("/index?logout")

Password hash compatibility. new BCryptPasswordEncoder(12, new SecureRandom("salt".getBytes())) seeds the salt RNG but does not change the hash format — BCrypt embeds the per-hash salt in the stored string. Replacing the seeded RNG with the default is therefore safe for existing rows in user.password; every stored $2a$12$… hash still verifies. Keep strength 12 to avoid needless rehash pressure.
GET /logout. With CSRF enabled Spring Security only accepts POST /logout by default; the explicit logoutRequestMatcher above is what keeps today's GET behaviour (templates/common/header.html links to /logout, login.service.ts line 22 issues a GET). A GET logout is itself a CSRF vector (a hidden <img src="/logout"> logs the user out). Recommended end state: drop the matcher, change the header link to a th:action="@{/logout}" POST form, and change AdminPortal to http.post; keep the matcher only as a transitional step until both callers are updated.
CSRF. Line 47 today is .csrf().disable().cors().disable(). Carrying csrf.disable() forward with cookie-based form login and remember-me leaves every POST in TransferController, AccountController and AppointmentController callable from a third-party page using the victim's session cookie. Thymeleaf's th:action injects the _csrf hidden field automatically once CSRF is on, so the 13 templates need no edits; AdminPortal (Angular Http, withCredentials) needs to read the XSRF-TOKEN cookie and send it as X-XSRF-TOKEN, which is why the repository is CookieCsrfTokenRepository.withHttpOnlyFalse(). Bootstrap matters: on a clean browser AdminPortal's very first request is the POST /index in login.service.ts line 10–18, so no cookie exists yet and Spring returns 403 before authentication. Two server-side changes make this work: (1) add .csrf(csrf -> csrf.csrfTokenRepository(…).csrfTokenRequestHandler(new CsrfTokenRequestAttributeHandler())) so the plain (non-XOR) cookie value is accepted from a JS client, and (2) expose a safe endpoint — GET /api/csrf returning 204, or simply the existing GET /index — that AdminPortal calls with withCredentials before the login POST so the cookie is set; the login then copies it into X-XSRF-TOKEN. Both go into step 2 together with the AdminPortal change, and the smoke test must run the login from a cookie-less client. If AdminPortal cannot be changed in the same release, scope the exemption to csrf.ignoringRequestMatchers("/api/**", "/index", "/logout") rather than disabling it globally.
Unused injections. Environment env (line 26) is injected but never read; remove it. UserSecurityService is now supplied through the DaoAuthenticationProvider bean rather than field injection.

config/RequestFilter.java compile recommend replace

Minimum change is the javax.servlet.* → jakarta.servlet.* import swap on lines 3-9. The recommended change is to delete the class: it hand-rolls CORS for the Angular origin http://localhost:4200, swallows exceptions from the chain (lines 24-28), and short-circuits every OPTIONS request before Spring Security sees it. Spring's CorsConfigurationSource does the same thing declaratively and integrates with the .cors() step enabled in the new SecurityConfig.

public class RequestFilter implements Filter {

                       FilterChain chain) {
    response.setHeader("Access-Control-Allow-Origin",

After · config/CorsConfig.java (new) — RequestFilter deleted
@Configuration
public class CorsConfig {

  @Bean
  public CorsConfigurationSource corsConfigurationSource(
      @Value("${app.cors.allowed-origin:http://localhost:4200}")
      String origin) {
    CorsConfiguration cfg = new CorsConfiguration();
    cfg.setAllowedOrigins(List.of(origin));
    cfg.setAllowedMethods(List.of("GET","POST","PUT","DELETE","OPTIONS"));
    cfg.setAllowedHeaders(List.of("authorization","content-type",
        "accept","origin","x-requested-with","x-xsrf-token"));
    cfg.setAllowCredentials(true);
    cfg.setMaxAge(3600L);

    UrlBasedCorsConfigurationSource src =
        new UrlBasedCorsConfigurationSource();
    // Match RequestFilter's scope (every path). AdminPortal
    // posts to /index, follows the 302 to /userFront, and
    // GETs /logout (login.service.ts:11,22) — a path list
    // would silently break the redirected login response.
    src.registerCorsConfiguration("/**", cfg);
    return src;
  }
}
Credentialed CORS. allowCredentials(true) plus a configurable origin means the value of CORS_ORIGIN in production must be the https:// AdminPortal origin, and server.servlet.session.cookie.secure=true / spring.security.rememberme cookies must be marked secure, otherwise the session cookie AdminPortal relies on is sent in clear text. The localhost:4200 default exists for local development only; fail startup if the property is unset in the prod profile.

If the team prefers the minimum-risk path for Step 2, keep the class and only change the four imports plus the doFilter signature to declare throws IOException, ServletException instead of catching Exception.

open-in-view. User.java lines 46-50 declare appointmentList and recipientList as FetchType.LAZY. An audit of the 13 templates finds neither collection is read through User: recipient.html and toSomeoneElse.html iterate the recipientList model attribute that TransactionServiceImpl.findRecipientList() builds from recipientDao.findAll(), and no template touches appointmentList. userRoles is EAGER. The templates are therefore safe, but the REST side is not: UserResource /api/user/all returns List<User> straight from UserServiceImpl.findUserList(), and while appointmentList (line 50) and userRoles (line 57) carry @JsonIgnore, recipientList (line 53–54) does not. With open-in-view=false the users are detached before Jackson calls getRecipientList(), and the admin listing returns 500 with LazyInitializationException. Today, with OSIV on by default, the same call already works — by serialising every user's recipients (names, account numbers, bank names) into the admin listing and issuing one extra query per user; AdminPortal's user.service.ts never reads that field. So add @JsonIgnore to recipientList in the step 1 entity pass (shown in the User.java diff above), which closes the data exposure and removes the N+1. Keep open-in-view enabled (set it to true explicitly so Boot stops warning) until that annotation is in; then flip it to false under the step 0 smoke suite, which must fully consume the /api/user/all body.

controller/*.java · resource/*.java compile clean two behaviour notes

All 7 web classes use @RequestMapping(value, method), @ModelAttribute, @RequestParam, @PathVariable, Principal and Model — all unchanged in Spring Framework 7. Two runtime differences matter:

  • Trailing-slash matching is off (Spring 6+). GET /transfer/recipient/ previously matched TransferController line 76; it now returns 404. Audit AdminPortal HTTP calls in AdminPortal/src/app/** for trailing slashes on /api/user/all, /api/appointment/all etc.
  • Date JSON format changed. UserResource returns List<PrimaryTransaction> / List<SavingsTransaction> and AppointmentResource returns List<Appointment>; each carries a java.util.Date date field. Boot's Jackson auto-configuration has disabled WRITE_DATES_AS_TIMESTAMPS since 1.2 and application.properties does not override it, so today's output is already an ISO-8601 string of the form "2017-06-14T20:00:00.000+0000". What moves is the shape of that string: Jackson 2.11+ (Boot 2.4+) writes the offset as +00:00, and Jackson 3 (Boot 4) changes further defaults (UTC default zone, java.time module built in). Do not add write-dates-as-timestamps=true — that would turn the strings into epoch numbers and create the very break the plan is trying to avoid. Instead capture a real Boot 1.5 response from /api/user/primary/transaction and /api/appointment/all in the step 0 baseline test and assert the migrated output parses identically in AdminPortal (new Date(tx.date) accepts both offset forms; string comparison or regex parsing does not).

Optional tidy-up: replace @RequestMapping(value=…, method=RequestMethod.GET) with @GetMapping/@PostMapping; and AppointmentController lines 43-45 (new SimpleDateFormat("yyyy-MM-dd hh:mm").parse(date)) should move to LocalDateTime.parse + @DateTimeFormat once Appointment.date becomes LocalDateTime. Neither is required for the upgrade.

service/UserServiceImpl/UserServiceImpl.java · AccountServiceImpl.java · TransactionServiceImpl.java compile clean

UserServiceImpl lines 9 and 36 import and inject the concrete BCryptPasswordEncoder. Spring registers the bean under the factory method's declared return type, so the PasswordEncoder passwordEncoder() bean shown in the new SecurityConfig does not satisfy that field and the context fails to start with NoSuchBeanDefinitionException. AccountServiceImpl line 15 keeps account numbers in a static int nextAccountNumber — that is a pre-existing correctness bug (resets on restart, not thread-safe), not a migration issue, but the migration branch is a natural place to flag it.

Schema management. spring.jpa.hibernate.ddl-auto=update against Hibernate 7 will also attempt to alter column types where Hibernate's default mapping has changed since 5.0 (e.g. double amount stays double, but boolean → bit(1) vs tinyint and Date → datetime(6) precision differences are common). Naming strategy is stable. Boot 1.5 and Boot 4 both apply CamelCaseToUnderscoresNamingStrategy (formerly SpringPhysicalNamingStrategy), so userId/primaryAccount already map to user_id/primary_account_user_id-style columns and will continue to. No column renames are triggered by the upgrade.

08Risks and mitigations

data Primary-key collision on first start

Cause: AUTO → TABLE generator. Mitigation: IDENTITY everywhere (§05); never run ddl-auto=update against production during migration.

security Public path regressions

/error/**/* is rejected by PathPatternParser; /console/** (H2 console) is public but no H2 dependency exists — remove it. authorizeHttpRequests also secures FORWARD/ERROR dispatches, so keep /error/** permitted.

contract AdminPortal JSON dates

ISO offset format +0000 → +00:00 (Jackson 2.11+) and Jackson 3 defaults on 3 endpoints. Mitigation: baseline fixture from Boot 1.5, assert parse-equivalence in step 1; if AdminPortal string-matches, pin spring.jackson.date-format to the old pattern.

contract Trailing slashes & CORS pre-flight

Spring 6 drops trailing-slash matching; deleting RequestFilter changes who answers OPTIONS. Mitigation: grep AdminPortal for URL literals; keep .cors() enabled so Spring answers pre-flight before authentication.

infra MySQL server version

Connector/J 9.x drops MySQL 5.6/5.7. Confirm the target server is 8.0+ or pin mysql-connector-j 8.4.x via <mysql.version> until it is.

low Thymeleaf 2.1 → 3.1

Templates use only th:fragment, th:href="@{…}", th:action, th:each, th:text, th:object. None of the 3.1-restricted web objects (#request, #session, #servletContext) appear. Legacy HTML5 mode is gone but all 13 templates are well-formed.
